# 数字金融洞察 · 写作指南

本指南供模型在撰写洞察报告时引用。包含工作流、标准模板、风格模板、小组件方法和格式规范。

---

## 一、工作流

### 完整路径（讨论→写作→转换）
1. 用户提出要写洞察报告（主题/材料）
2. 与用户讨论确定：核心论点、风格选择、大纲结构
3. 写完整 Markdown 报告
4. 运行 gen_insight_doc.py 脚本生成 .docx

### 快速路径（仅转换）
用户直接提供 Markdown 文件 → 运行 gen_insight_doc.py 脚本生成 .docx

两条路径互不依赖。

## 二、大标准模板

### 通用骨架
| 组成部分 | 说明 |
|---------|------|
| 引言 | 有分量感，不平铺"某天某地开了个会" |
| 正文 | 由所选风格决定展开方式 |
| 银行视角 | 回到"对银行意味着什么" |
| 结论 | 点题不点人 |

### 八条宪法

1. **引言必有分量感**——不平铺事件，先给"为什么要读"的理由
2. **洞察融在行文中**——不贴"洞察"标签，由叙事自然推出
3. **标题编号固定**——一、→（一）→ 1. →（1），不用"洞察""分析"做标题
4. **银行视角收束**——无论主题多远，最终回到"对银行意味着什么"
5. **数据锚定论点**——关键判断必有数据或案例，不用"我们认为""笔者认为"
6. **类比克制使用**——只在核心概念处用一次，不反复堆砌
7. **结论点题不点人**——结论回到主题本身，不重复人物/公司名字
8. **中文引号规范**——使用""、''，不用英文引号

### 通用 Prompt 模板（每次写前注入）

```
## 洞察报告写作标准

你正在撰写《数字金融洞察》报告。遵守以下通用规范：

1. 引言有分量感——不平铺事件，先给"为什么要读"的理由
2. 洞察融在行文中——由叙事推出，不贴"洞察"标签
3. 标题编号：一、→（一）→ 1. →（1），不用元标签
4. 银行视角收束——回到"对银行意味着什么"
5. 数据锚定论点——关键判断必有数据，不用"我们认为"
6. 类比克制——核心概念处最多一次
7. 结论点题不点人
8. 中文引号

风格选择：{STYLE}
主题材料：{MATERIALS}
```

## 三、风格选择

### 决策树

```
你要写什么？
│
├─ 外部提出了颠覆性理论/框架 → A 理论建构型
│   给读者一副"看问题的眼镜"
│   例：某分析师提出新范式、某公司发布技术革命
│
├─ 行业发生了重大事件/趋势   → B 事件驱动型
│   给读者一张"行动路线图"
│   例：政策出台、产品爆发、巨头发布新协议
│
└─ 同业做出了值得研究的实践  → C 同业深研型
    给读者一套"可迁移方法论"
    例：某银行战略升级、某金融机构发布新产品
```

### 混合风格
内容同时包含框架+产品+对标时，选主导风格，融辅助风格的事件密度。
- A+B：A骨架 + B事件密度（框架建构法 + 事件排比法）
- A+C：A框架 + C案例深研（框架建构法 + 模式提炼法）
- B+C：B节奏 + C深度（事件排比法 + 模式提炼法）

## 四、风格模板

### 风格A：理论建构型

**开头（三段式）**
```
① 人物/理论背景 → ② 事件与核心论点 → ③ 为什么重要
```

**正文骨架**
1. 框架总览——一句话定义核心框架，让读者先拿到"地图"
2. 逐层拆解——每层是框架的组成部分，不是事件的组成部分
3. 类比锚定——核心概念处用一次类比，之后不再重复
4. 推论展开——从框架自然推出"这意味着什么"

**银行视角**：放在结论段，用框架重新审视银行

**Prompt 模板**
```
## 风格 A：理论建构型

【开头】三段式：① 人物/理论背景 ② 事件与论点 ③ 为什么重要
【正文】① 定义框架 ② 逐层拆解（每层是框架组成部分） ③ 类比锚定 ④ 推论展开
【银行视角】放在结论段，用框架重新审视银行
【结论】回到框架价值，点题不点人

核心框架：{FRAMEWORK}
类比设计：{ANALOGY}
材料：{MATERIALS}
```

---

### 风格B：事件驱动型

**开头（三层递进）**
```
① 事实排比 → ② 信号判断 → ③ 本文定位
```

**正文骨架**
1. 行业动态——多个玩家/产品密集排比，形成"浪潮"感
2. 框架归类——用一个框架归类散乱事件
3. 银行影响——结构性影响逐条展开，每条"标题+一句话+展开"
4. 行动建议——具体可操作，指向下一步行动

**银行视角**：独立章节，占全文1/3–1/2，分"结构性影响"和"行动建议"

**Prompt 模板**
```
## 风格 B：事件驱动型

【开头】三层递进：① 事实排比（2-3个） ② 信号判断 ③ 本文定位
【正文】四段式：① 行业动态 ② 框架归类 ③ 银行影响 ④ 行动建议
【银行视角】独立章节，占全文1/3-1/2
每条影响=小标题+一句话+展开
【结论】回到事件的长远含义

核心事件：{EVENT}
归类框架：{FRAMEWORK}
材料：{MATERIALS}
```

---

### 风格C：同业深研型

**开头（三段）**
```
① 亮成绩数字 → ② 能力归因 → ③ 报告定位
```

**正文骨架**
1. 产品/能力拆解——每个模块独立成章，内部"做了什么→怎么做到→效果如何"
2. 模式提炼——从拆解中归纳可迁移模式（双轨制/飞轮/闭环）
3. 价值验证——用数据证明模式有效

**银行视角**：独立章节，占全文1/4–1/3，每条启示与正文拆解紧密呼应

**Prompt 模板**
```
## 风格 C：同业深研型

【开头】三段：① 亮成绩数字 ② 能力归因 ③ 报告定位
【正文】拆解→提炼→验证：
① 产品/能力拆解（每模块：做了什么→怎么做到→效果如何）
② 模式提炼（命名≤6字）
③ 价值验证（数据证明有效）
【银行视角】独立章节，占全文1/4-1/3
每条启示从"对方怎么做"推导出"我们可以怎么做"
【结论】回到方法论的可迁移性

研究对象：{SUBJECT}
核心能力：{CAPABILITIES}
材料：{MATERIALS}
```

## 五、8个小组件方法

### 方法1：开头三段式
**写法**：① 引力钩（A=人物权威、B=事实冲击、C=成绩数字）→ ② 核心信息 → ③ 本文定位

### 方法2：洞察嵌入三手法
- **因果链**：从事实A推出结论B。"用户不打开App→注意力不再是标的→信任度取代注意力"
- **矛盾悖论**：用反直觉揭示深层逻辑。"Token价格跌90%，消耗量反暴增——杰文斯悖论"
- **模式提炼**：从拆解归纳可迁移模式。"FDE现场服务→能力沉淀回中台→服务成本下降→这不是外包"
- **判断标准**：去掉"洞察"二字后，段落仍应有分析力度。

### 方法3：类比锚定法
**写法**：① 只在核心概念处一次 ② 类比必须映射框架结构 ③ 类比后立即回正文
**示例**：摩尔定律=盖平房越盖越小；韬定律=盖多层楼房优化道路

### 方法4：银行视角收束法
**三级递进**：① 发生了什么变化 → ② 这意味着什么 → ③ 需要做什么
**禁止**："建议重视""应密切关注"等空话

### 方法5：数据锚定法
**规则**：① 关键判断必有数字/案例 ② 数据有比较维度 ③ 数据后跟解读
**对比**：❌"AI支付增长很快" ✅"累计突破3亿笔，覆盖95%框架——从工具变成事实标准"

### 方法6：框架建构法
**写法**：① 一句话定义框架 ② 按框架组成部分展开 ③ 层层递进 ④ 推出推论
**要求**：每层是框架组成部分，不是事件组成部分

### 方法7：事件排比法
**写法**：① 选2-4个关键事件 ② 每个一句话 ③ 排比后紧跟归纳句

### 方法8：模式提炼法
**写法**：① 识别共性逻辑 ② 简短命名（≤6字，如双轨制/飞轮）③ 数据验证 ④ 明确迁移边界

## 六、格式规范（供 gen-insight-doc 脚本使用）

### 标题编号规则
- 一级标题：一、二、三、...
- 二级标题：（一）（二）（三）...
- 三级标题：1. 2. 3. ...
- 四级标题：（1）（2）（3）...

### Markdown 映射规则
| 原始写法 | 对应输出 |
|---------|---------|
| `# 标题` | 文档大标题（居中、蓝色、22pt） |
| `## 一、...` 或 `## 标题` | 一级标题（方正黑体、16pt） |
| `### （一）...` | 二级标题（方正楷体、16pt） |
| `#### 1. ...` | 三级标题（方正仿宋、16pt） |
| `（1）...` | 四级标题（方正仿宋、16pt） |
| `内容提供：...` | 内容提供行（居中、16pt、加粗） |

### 内容提供行
固定在引言之前：`内容提供：数金办创新团队洞察小助`

### 其他规范
- 中文语境使用中文引号""、''
- 全文首行缩进2字符（大标题和"内容提供"行除外）
- 行距1.2倍，两端对齐
- 三号字（16pt）
